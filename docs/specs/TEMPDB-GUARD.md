# TEMPDB-GUARD — tempdb guard rail (alert + self-attributed stop)

> **DRAFT** — source of truth for the intended behavior of tempdb monitoring.
> Cross-cutting mini-spec: it serves **all** drivers (`SORT_IN_TEMPDB` rebuild, shrink, batched
> DML), not just DML. Nothing is implemented yet.

## 1. Goal and context

tempdb is a resource **shared by the whole instance**: filling it up doesn't just break the target
database, it breaks *every* database. The blast radius justifies a guard rail even if the event is
rare. Several SqlGoPace operations **consume** tempdb: the sort of a `SORT_IN_TEMPDB` rebuild,
sort/hash spills of a large chunked DML (`docs/specs/BATCH-DML.md`), and — under RCSI — the version store
generated by a batched UPDATE/DELETE.

The central trap is **attribution**: monitoring the user database's log works because log pressure
*is* mostly caused by our own DDL; tempdb pressure, **often not**. If a *third party* fills tempdb,
pausing **our** operation **frees nothing** — we penalize ourselves for someone else's fault. This
guard rail solves that by **measuring our own tempdb usage** before deciding to stop.

> Guiding principle: **always alert, stop only when it's us** (and therefore only when stopping
> actually relieves tempdb).

## 2. Three postures, by increasing severity

1. **Preflight — don't start.** If tempdb is **already** above the threshold at preflight time, the
   op fails cleanly (routed to `04.failed`, no locks taken) with an actionable message. Extends
   `internal/preflight` on the `CheckLog` model.
2. **Runtime — alert (TUI + log), without stopping.** As soon as tempdb crosses a threshold during a
   run, we emit an **informational incident** to the TUI and the `.log`. This is information, not a
   decision: it never lies and never penalizes us. Cost = one more DMV read on the existing sampling
   cadence.
3. **Runtime — stop conditioned on self-attribution.** We escalate to a **stop** (pause if resumable
   → cancel) **only** if **both** are true:
   - tempdb is above the cap, **and**
   - **our** executing session is a **material** contributor (see §3).

   Otherwise (tempdb pressure but it isn't us) → **alert only**.

## 3. Detection (DMVs, reads — all cheap)

- **Our usage**: `sys.dm_db_session_space_usage` filtered on the **executing SPID** (the engine
  already knows it — it's the one used for KILL and per-session waits). The **net held** =
  `(user_objects_alloc − user_objects_dealloc) + (internal_objects_alloc − internal_objects_dealloc)`
  pages × 8 KB. This is the *actionable* signal (what we hold right now, not the cumulative total),
  and it captures exactly the cases where stopping **frees** space: `SORT_IN_TEMPDB` sort, sort/hash
  spill.
- **Global tempdb view**: `sys.dm_db_file_space_usage` (allocated/free extents + `version_store_`,
  `internal_objects_`, `user_objects_reserved_page_count`) and the tempdb file sizes. Gives the
  "fill percentage" compared to the cap, both data and log for tempdb.
- **Material contributor** = net held by our SPID above an absolute threshold (MB) **or** above a
  share of tempdb in use (configurable). Conservative default: an absolute threshold in MB.

`VIEW SERVER STATE` (already required for monitoring, see `docs/e2e.md`) is enough for these reads.

## 4. The accepted blind spot: the version store (RCSI)

The RCSI / chunked DML case is precisely the one where per-session attribution **breaks**, and we
accept it:

- The version store is **not** counted in `dm_db_session_space_usage` (those are internal/user
  objects, not versions). Versions are attributed to the *transaction* and pinned by *readers*;
  there is no **cheap** per-session DMV that says "you generated X MB of version store".
- But our batches **commit one at a time**: *our* transaction pins almost nothing. A version store
  that grows is held by a **long-running reader**, not by us → **stopping doesn't free it**.

So for the version store: **alert only**, never an automatic stop. This is consistent with the
principle (§1) — if it isn't our *actionable* fault, we don't stop. We don't pretend to attribute
what we can't attribute cleanly.

## 5. Integration (reuses the existing plumbing)

- **New pressure dimension** in `internal/run/reaction.go`: `Pressure.TempdbOverCap bool` +
  `Pressure.TempdbSelfDriven bool`. The reaction decision stays unchanged for everything else; we
  add: *always alert on `TempdbOverCap`; escalate to a stop only if
  `TempdbOverCap && TempdbSelfDriven`*. (Same spirit as `BlockingOthers` + filtering.)
- **Sampling**: the tempdb read (global + our SPID) hooks into `pumpSamples`
  (`internal/run/executor.go`), on its own cadence like the log — a `TempdbSample` parallel to
  `LogSample`. It therefore covers `MonitoredRunner` **and** `ShrinkRunner` **and** the future
  `BatchDMLRunner` with no per-driver code.
- **Alert**: surfaced as an **informational incident** through the channel already used for narration
  (engine sink/feed → TUI incident console + `.log`), with a distinct *kind* (`tempdb`) so it reads
  as a warning, not as a destructive reaction.
- **Self-attributed stop**: goes through the existing reaction hierarchy (pause resumable → cancel);
  cancelling/rolling back a sort returns the internal pages → genuinely relieves tempdb.

## 6. Wiring (by layer)

- **`internal/mssql`** — new reads: `TempdbSpace(ctx) (TempdbSpace, error)` (global, via
  `sys.dm_db_file_space_usage` + file sizes) and `SessionTempdbMB(ctx, spid int) (int, error)`
  (net held, via `sys.dm_db_session_space_usage`). Exposed to `internal/run` behind a narrow
  interface (`ShrinkReader` model).
- **`internal/run/executor.go`** — `TempdbSample` + the read in `pumpSamples`; computes
  `TempdbOverCap`/`TempdbSelfDriven` from the thresholds.
- **`internal/run/reaction.go`** — the two `Pressure` fields + the "alert vs stop" rule.
- **`internal/preflight/preflight.go`** — `CheckTempdb(space, cap)` on the `CheckLog` model (Fail if
  already above, Warn when close to the threshold).
- **`internal/config/config.go`** — `TempdbConfig`: `preflight_max_*`, `alert_max_*`,
  `self_contribution_min_mb` (the "material" threshold), tempdb poll cadence.
- **TUI / report** — display the tempdb incident (TUI) and write it to the `.log`.

## 7. Phasing

- **It1.** `mssql` reads (global + per SPID); **preflight no-start**; **runtime alert** to TUI/log on
  threshold. No automatic stop. Already covers most of the value (visibility + do no further harm).
- **It2.** **Self-attributed stop**: `TempdbSelfDriven` via `sys.dm_db_session_space_usage`,
  conditional escalation in the reaction (pause/cancel) when we are the material contributor.
- **It3 (optional).** Refine "material" as a share of tempdb in use rather than an absolute value;
  surface the breakdown (user objects vs internal objects vs version store) in the incident.

## 8. Tests (no database; `-race`)

- **preflight:** `CheckTempdb` Fail above the cap, Warn when close, Pass otherwise (table-driven,
  like `CheckLog`).
- **run (pure):** the reaction rule — `TempdbOverCap` alone ⇒ **alert, no stop**;
  `TempdbOverCap && TempdbSelfDriven` ⇒ stop (pause if resumable, otherwise cancel); neither ⇒
  nothing. Computing the net held per SPID from simulated alloc/dealloc counters.
- **mssql:** both queries behind the `integration` tag.

## 9. Limits (deliberate, documented)

1. **Version store not cheaply attributable per session** → alert only for that case (§4).
2. **The "material" threshold is a heuristic**: too low and we stop for very little; too high and we
   miss our own drift. Configurable, conservative default in absolute MB.
3. **Sampling race**: tempdb pressure is read on a cadence; a very fast drift between two samples may
   only be seen on the next tick — acceptable (rare, and preflight covers the initial state).
4. **Multiple sessions**: we only attribute to the **executing SPID**; a possible side session
   (monitoring) doesn't consume significant tempdb, so it is ignored.
