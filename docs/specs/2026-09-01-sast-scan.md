## 1. `.env` is world-readable by the tool's own documented workflow — MODERATE

**Location:** `internal/scaffold/scaffold.go:95`, with `docs/getting-started.md:77`

`scaffold` writes every asset with `os.WriteFile(p, body, 0o644)`, including `.env.example`.
`docs/getting-started.md:77` then instructs `cp .env.example .env`.

`cp` (without `-p`) creates the destination with the source's mode bits masked by the user's
umask. Under the near-universal default `022`, `0644` passes through unchanged, so the
resulting `.env` is `0644`. That file holds `DB_PASSWORD` and `WEBHOOK_URL`
(`internal/scaffold/assets/env.example`). An operator running a restrictive umask such as `077`
is not affected — which is precisely why this cannot be left to chance.

**What goes wrong:** on any Linux or macOS host, every local user can read the SQL Server
credentials. The login SqlGoPace needs is not a small one — `VIEW SERVER STATE` plus `ALTER`
on the target objects, and in practice often `sysadmin`. On a shared DBA jump box, that is a
production credential handed to everyone with a shell.

**Who it happens to:** the default path, on the platforms the release workflow cross-compiles
for. Windows is unaffected — Go's file mode maps only to the read-only bit there, which is why
this survives unnoticed by an author working on Windows.

**Smallest fix (code):** write `.env.example` at `0o600`; `cp` then propagates the safe mode.
Optionally have `init` warn when an existing `.env` is group- or world-readable.

## 2. Blocked-session captures expose third-party SQL text at 0644 — MODERATE

**Location:** `internal/run/capture.go:144`, `internal/run/contended.go:158`,
`internal/run/amplifier_capture.go:158`; directories at `internal/run/queue.go:35` (`0o755`)

`renderCapture` writes, per blocking session, `login_name`, `host_name`, `app_name`,
`active_query` and `parent_query` — **the SQL text of other people's sessions**, captured from
the DMVs while our DDL waited.

**What goes wrong:** ad-hoc application SQL routinely carries literal parameter values.
Whatever those are on the target server — identifiers, addresses, account numbers — lands in a
world-readable file under `02.processing/`, alongside the logins and hostnames that ran them.
The operator never chose to persist this; it is a side effect of being blocked.

**Who it happens to:** the default path, whenever anything blocks the DDL. Linux/macOS only,
as above.

**Smallest fix (code):** `0o600` on the three capture writes and `0o700` on the queue
directories. These files are advisory — SqlGoPace never reads them back — so tightening the
mode costs nothing.

## 3. Release workflow interpolates a tag into a run step with contents:write — MODERATE

**Location:** `.github/workflows/release.yml:31` and `:93` (semgrep `run-shell-injection`)

The tag is taken as `github.event.inputs.tag || github.ref_name` and interpolated directly into
a `run:` block. GitHub substitutes textually before the shell parses the line. Git ref names
permit `;`, `$`, backticks and `&`, and a `workflow_dispatch` input is free-form, so either
trigger can close the quote and append commands. The job holds `permissions: contents: write`
and the `Publish` step has `GH_TOKEN`.

**What goes wrong:** arbitrary code on the runner with a token that can overwrite published
release assets — i.e. replace the binaries strangers download and point at production.

**Who it happens to:** requires push access to the repository, so today it is the author alone.
It becomes real the moment a second maintainer exists or a credential leaks. Reported because
this tool is about to be advertised, and its release artifacts are its trust boundary.

**Smallest fix (code):** bind the expression to an `env:` variable on the step and reference it
as `"$TAG"` in the script. The shell then never sees attacker-controlled text.

## 4. Release actions pinned to mutable major tags — MODERATE

**Location:** `.github/workflows/release.yml:19,22`; `.github/workflows/ci.yml:12,13,33,34,44`

`actions/checkout@v7`, `actions/setup-go@v7`, `golangci/golangci-lint-action@v9`. A major tag
is a moving pointer the action owner can repoint. This is not theoretical — it is how
`tj-actions/changed-files` and `reviewdog` were used to exfiltrate secrets in 2025.

**What goes wrong:** a compromised upstream action runs with `contents: write` during the
release job and tampers with the binaries. Unlike finding 3, **this needs no access to your
repository at all.**

**Who it happens to:** anyone downloading a release built after the upstream compromise.

**Smallest fix (code):** pin to full commit SHAs in `release.yml` at minimum. `ci.yml` matters
less — it publishes nothing.

## 6. SMTP tls.Config sets no MinVersion — MINOR

**Location:** `internal/report/email.go:127`

`c.StartTLS(&tls.Config{ServerName: cfg.Host})`. **Not a live exposure:** Go has defaulted
client `MinVersion` to TLS 1.2 since 1.22, which semgrep's own message concedes. Setting
`MinVersion: tls.VersionTLS12` explicitly makes the guarantee independent of the toolchain
default.

Checked while triaging: when `cfg.StartTLS` is false, credentials are *not* leaked — Go's
`smtp.PlainAuth` refuses to send over an unencrypted non-localhost connection. That guard is
the standard library's, not this code's.

## What the scanners could not see

**`gosec` reported zero G201/G202 — no SQL injection — from a codebase whose entire purpose is
building T-SQL by string concatenation.** That is a false negative, not a clean bill.

G201 fires when a formatted string reaches `db.Query`/`Exec` *within one function*. Here
`internal/ddl` builds statements as pure string functions and returns them; `internal/mssql`
executes a string variable that arrives as a parameter. The taint crosses a package boundary,
so the AST rule never sees a source and a sink together. `SECURITY.md:53` names two fields —
`set_raw` and `where_raw` — as interpolated verbatim into the generated statement; the harm
review counted four in total. No scanner flagged any of them. (The count of four is carried
from that review, not re-verified in this SAST-only pass; the two in `SECURITY.md` are.)

CWE-89 is the CWE most relevant to this tool, and the scanner floor is blind to it. Likewise
CWE-400: the loops, held locks and unbounded waits that decide whether this tool hangs a
production server are invisible to all three tools. Treat this document as the floor it is.

## Reproducing this scan

```bash
gosec -fmt=json -quiet ./...
govulncheck ./...
semgrep --config auto --json --quiet --exclude=formation --exclude=local .
```

Behind a TLS-intercepting proxy, `semgrep --config auto` fails to reach the rule registry with
`CERTIFICATE_VERIFY_FAILED`. Export the Windows root store to a PEM, append semgrep's bundled
`certifi/cacert.pem`, and point `REQUESTS_CA_BUNDLE` and `SSL_CERT_FILE` at the result. The
`uv tool install --system-certs` flag covers the install but not semgrep's own HTTP calls.
