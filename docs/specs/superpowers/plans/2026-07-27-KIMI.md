# Plan review: 2026-07-27-shrink-tempdb.md

Status: issues found. The plan is detailed, actionable, and mostly well-sequenced, but it has one logical inconsistency and a missing preflight task that would block or mislead implementation.

## Issues (would affect execution)

1. `NoProgressBeforeFlush` default contradicts its own constraint.

   The Global Constraints section states:

   > `NoProgressBeforeFlush` default = 3, must be `< MaxNoProgress` (3 today)

   `3 < 3` is false. Looking at the Task 7 implementation, the flush check runs before the max-no-progress give-up, so `NoProgressBeforeFlush == MaxNoProgress` technically works (the flush fires on the third stall, then the counter resets). But the wording is confusing and leaves the default at the very last moment, giving no retry room after the flush. The default should be `2`, or the constraint should say `<= MaxNoProgress`.

2. Preflight is missing as a task.

   The spec §6 and §7 explicitly require `internal/preflight` to verify tempdb reachability and the target files exist, and to state the total target size. The plan never touches `internal/preflight`. Without it, the operation will fail the schema/table existence check or skip the database-scoped checks the spec demands. This should be a dedicated task, likely between Tasks 3 and 4, or merged into Task 8 with a preflight helper.

3. No validation enforces `NoProgressBeforeFlush < MaxNoProgress`.

   The global constraint says the value must be below `MaxNoProgress`, but Task 4 only sets a default. `config.Validate` (if it exists) should reject a config where `NoProgressBeforeFlush >= MaxNoProgress`; otherwise the stall ladder behaves unexpectedly.

4. Task 7 second test is a skeleton.

   `TestTempdb845IsRetryableNotFatal` has a comment describing intent but no assertions. If left as-is, it will pass vacuously and not actually guard the 845 behavior.

## Recommendations (advisory)

- Set `NoProgressBeforeFlush` default to `2` and update the global constraint to `<= MaxNoProgress`.
- Add a preflight task: verify tempdb is reachable, enumerate data files, and emit the "total target" message. Reuse the existing shrink preflight pattern but skip the schema/table existence check.
- Add a config validation rule (or at least a runtime guard) ensuring `NoProgressBeforeFlush < MaxNoProgress`.
- Flesh out the 845 test with concrete fake setup and assertions.
- In Task 9, reword "it lazily connects" because `OpenScoped` opens the connection immediately.
- Consider a note that the optional `aggressive` `('ALL')` flush widening from the spec is deliberately deferred.

## What is strong

- The task decomposition is clear: pure core first, then config, then mssql detector, then runner refactor, then escalation, then orchestration, then wiring, then docs.
- Each task follows TDD: failing test, implementation, verification, commit.
- The plan directly addresses the spec-review concerns from `docs/specs/TEMPDB-SHRINK-KIMI.md`:
  - `Target()` returns `ObjectRef{Database: "tempdb"}` (Task 1).
  - `NoProgressBeforeFlush` default is defined (Task 4).
  - The two-phase TRUNCATEONLY order is explicit via `RunTempdb` (Task 8).
  - Routing is solved with a new `TempdbShrinkDriver` interface (Task 8).
  - The unbalanced-files warning is implemented (Task 8).
- Reuses existing primitives (`chunkLoop`, `runTruncateOnly`, `resolveFiles`) instead of duplicating the loop.
- Includes the `/simplify` pass and code-review skill references required by CLAUDE.md.
- Version bump and README/operator-skill updates are included.

## Verdict

The plan is executable after fixing the `NoProgressBeforeFlush` default/constraint and adding the missing preflight task. With those two fixes, it is ready for implementation.
