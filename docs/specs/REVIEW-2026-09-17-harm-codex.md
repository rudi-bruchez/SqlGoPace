# SqlGoPace production-harm review

## 1. What this software can do to production

It can remove application data/constraints, block production, roll back unrelated transactions, exhaust shared storage/CPU/I/O, discard resumable build progress, and repeat or silently skip work. Its strongest-sounding protections are sampled reactions and local bookkeeping, not hard safety boundaries. The unchanged scaffold example is disabled; these hazards begin when an operator queues maintenance or invokes --auto.

The most important confirmed defects are fail-open monitoring, shrink phases that ignore normal pressure, shrink targets that do not preserve reserve space, and recovery state that does not identify the full work being resumed. Default certificate trust and unbound session-number KILL add exploitable security risks. No physical storage corruption or catastrophic autonomous deletion was demonstrated; arbitrary trusted raw SQL and explicit drop/delete operations can nevertheless cause catastrophic data loss.

Scope: current clone. Docker unavailable; no database connected. SQL Server consequences are source-based inferences unless explicitly stated otherwise. Seven deterministic characterization tests reproduced controller/config/recovery behavior, and the database-free suite passed under a separate Go 1.26.5 test module. See verification at the end.

The findings below are strictly ordered by estimated harm to the stated stranger: common default-path outage/resource risks first, then recovery/data effects, conditional control/security risks, and narrower operational defects. Severity describes impact; ordering also weighs exposure and likelihood. IDs preserve the order in which findings were appended during investigation, not rank.
## F16 — SEVERE — Shipped resource guards do not prevent a full volume or a saturated production server
Location: config.yaml:28–39, :47–48; internal/preflight/preflight.go:148–189; internal/preflight/sizes.go:18; internal/run/executor.go:402; maintenance_profile.yaml:15, :47–55.
Who: default path on an ordinarily configured production database; particularly large rebuilds, online operations and --auto.
Input: rebuild a 100 GB index with data autogrowth unlimited on a volume with 2 GB free. require_data_free_space:true warns and runs; it checks neither the volume nor destination filegroup, and unreadable object sizes also warn/run. create_index, add_constraint and alter_column do not receive this size check. An allocated 500 GB log containing only 1 GB used passes log_max_size_bytes:50GB, because the guard measures used bytes, not physical allocation. Healthy CPU/I/O saturation triggers no reaction; MAXDOP is unset by default. FULL recovery without log backup keeps committed batch log records; RCSI/versioning can fill tempdb even when the monitored user log is below cap. The 60-second log polling interval plus cancellation/rollback latency permits overshoot. A default Standard offline rebuild can block for approximately a polling delay plus a minute, then spend unbounded time rolling back and immediately retry once.
Evidence: default values, measured quantities, checked operation types and lack of volume/tempdb/CPU reaction paths. Consequences are inferred. README does accurately disclose the disk and Standard-edition limits; this is a production hazard, not an undisclosed defect. “50 GB absolute ceiling” in both shipped configs is MORE REASSURING than a sampled used-byte trigger.
Smallest fix: fail closed on unknown essential capacity, check the destination volume/filegroup and tempdb budget, distinguish log allocation from used bytes, choose conservative concurrency/MAXDOP and require explicit acceptance of heavy offline work. Reserve rollback headroom rather than treating the reaction threshold as a hard cap.

## F01 — SEVERE — Monitoring fails open, and one stuck monitoring query disables both safety channels
Location: internal/run/executor.go:289 (pumpSamples), :402 (ServerSampler.Log).
Who: default path after a monitoring permission/network/query failure.
Scenario: shipped config, ordinary rebuild_index on a large production table; execution remains healthy but ActiveSessions or LogSpace fails or stalls. Both polls run serially, without their own deadlines. Errors are discarded; initially healthy cached values remain healthy, and no failure is reported to the supervisor. Additionally, LogSpace can successfully establish that the log exceeds 50 GB/80%, but a failing LogReuseWait query discards that alarm. DDL continues with locks and log generation indefinitely; a blocked metadata query also prevents the other poll from running. A sample-driven max_block_minutes or graceful pause cannot rescue a pump that sends no samples.
Evidence: pumpSamples only sends on err == nil; synchronous sampler calls share the operation context; Log returns an empty sample plus error if the descriptive reuse-wait query fails. This walks past the advertised continuous monitoring and log ceiling without changing any safety key.
Smallest fix: bounded independent monitoring queries, explicit freshness/error state, fail closed after a short monitoring-loss budget; preserve OverCap=true when only reuse-wait attribution fails.

## F07 — SEVERE — Default shrink phases explicitly discard blocking/log pressure
Location: internal/run/shrink.go:807–861 (runWatchedStatement); internal/ddl/generate.go:315; docs/blocking-and-kills.md:73.
Who: default shrink/shrink_tempdb path; no unsafe override needed.
Input: operations: [{operation: shrink, type: data, files: all, targetfreespace: "10%"}] with the shipped one-minute blocking timeout and no max_block_minutes. Every data shrink starts with TRUNCATEONLY. That phase (and the entire log shrink) drains pressure samples but immediately continues whenever maxBlock <= 0. It never applies blocking_timeout_minutes or LogOverCap. TRUNCATEONLY SQL does not carry WAIT_AT_LOW_PRIORITY. A contended phase can block the application or wait indefinitely; the advertised normal yield hierarchy does not act. With max_block_minutes set, only continuous blocking is acted on, never log pressure.
Evidence: source control flow explicitly limits this phase to opt-in max-block and operator graceful stop. No SQL reproduction. The documentation's default good-citizen yielding and always-honoured log protection are MORE REASSURING THAN THE CODE.
Smallest fix: use the normal supervisor for these cancel-safe phases too; retain explicit drain handling and apply default blocking and log thresholds even when max_block_minutes is absent.

## F20 — SEVERE — TRUNCATEONLY can remove the free-space reserve or shrink tempdb below the requested size
Location: internal/run/shrink.go:289–345, :373–429; internal/ddl/generate.go:304–305; docs/shrink.md:39.
Who: default data-shrink and tempdb-shrink algorithm, even with a carefully chosen target.
Input: a 1000 MB data file using 100 MB near its front, targetfreespace: 100MB. The calculated target is 200 MB, but the first generated statement is DBCC SHRINKFILE (file, TRUNCATEONLY), with NO size target. If the trailing free extents can be released down to roughly 100 MB, the code accepts size <= final as success; it does not preserve the requested 100 MB free reserve. tempdb's Phase 0 does the same to every data file before checking whether each is already below targetsizemb. An already correctly sized tempdb can therefore be shrunk unnecessarily and asymmetrically. Subsequent workload must regrow files; with autogrowth disabled it instead runs out of space.
Evidence: generated SQL and postcondition, not a SQL Server reproduction; exact attainable size depends on allocated extents/minimum file size. The input explicitly needs a file whose minimum/extent layout permits that truncation. Docs describing free space “wanted in the final file” are MORE REASSURING THAN THE CODE.
Smallest fix: omit the unbounded TRUNCATEONLY pass when a reserve/absolute target matters; use a size-respecting operation and verify the resulting reserve. Gate tempdb files before any mutation and do not classify overshrink as an unqualified success.

## F09 — SEVERE — Five-minute self-wait limits do not bound a blocked statement, and cancellation can wait forever
Location: internal/run/batch_dml.go:357–374, :394–438; internal/run/shrink.go:699–762, :976; internal/run/monitored_runner.go:208–230, :243; internal/run/executor.go:228.
Who: default batches/shrink; all runners on cancellation failure.
Input: an application transaction holds a conflicting lock while batch_update waits; it blocks no other session, and log usage stays below cap. supervise only reacts to OUR blocking others or log pressure. Batch SelfWaitTimeout is checked after awaitRelief returns and counts only that relief wait, not time inside runBatch. Shrink's corresponding budget counts backoff sleeps after a chunk finishes, not its live lock wait. A pre-2022 shrink without WALP can therefore wait forever despite self_wait_timeout_minutes: 5. waitForRelief also has no blocking timeout, and its log deadline is evaluated only upon a sample.
Cancellation: after the 30-second grace all three runners issue KILL with context.Background and then receive from done without a timeout. Failure/absence of ALTER ANY CONNECTION, hung control connection or long rollback can retain locks and the queue lock indefinitely. Hard context cancellation returns Continue from supervise, bypassing the explicit KILL fallback entirely; deferred cancellation alone is left to stop SQL.
Evidence: source control flow; consequences not tested against SQL Server. Docs' “max cumulative wait while blocked” is MORE REASSURING THAN THE CODE.
Smallest fix: measure self-blocking in flight on a monotonic budget; bound control queries and joins, preserve unresolved state, and apply fallback logic to hard cancellation as well. Never claim rollback completion merely because the client call returned.

## F05 — SEVERE — Resume fingerprints ignore operation contents; stale watermarks can silently skip new work
Location: internal/run/engine.go:1810–1850; internal/run/batch_watermark.go:69; internal/run/batch_dml.go:255.
Who: interrupted/default recovery path after editing or reusing a manifest.
Scenario A: finish op 0 batch_update on dbo.Orders with set: {Archived: 1}, stop before op 1, then change op 0 to set: {Archived: 0}. Command and target remain identical, so fingerprint matches and resume cursor skips the changed operation. Changing compression or partition on the same index has the same problem.
Scenario B: interrupt the FIRST key_range operation after watermark 10000; replace its table or filter and re-run the same filename. resumeFromOp is still 0, so reconcileResumePlan does not even compare fingerprints or clear watermarks. Smallest fix: fingerprint the complete normalized operation and resolved target/database; validate it even at cursor zero and bind every watermark and paused record to it. Refuse an edited interrupted plan rather than silently restarting destructive work.

## F08 — SEVERE — Crash recovery can replay committed, non-idempotent effects
Location: internal/run/engine.go:1775–1801; internal/run/batch_dml.go:245–322; internal/ddl/batch.go:208; internal/run/batch_watermark.go:15.
Who: batch_update key_range opt-in; ordinary crash/restart or continue-on-failure interruption.
Concrete input: batch_update dbo.Orders, set: {Archived: 1}, confirm_full_table: true, batch: {strategy: key_range}, on a table with a unique integer clustered Id and an AFTER UPDATE trigger that appends a billing/audit event. Crash after a range UPDATE commits but before its local watermark is saved. Recovery repeats the boundary range. The literal Archived value is idempotent, but the trigger is not: it fires again even for already-Archived rows, because key-range UPDATE has no self-limiting predicate. Local SQL commits and watermark/cursor writes cannot be atomic together. Best-effort watermark failures widen the replay range.
A failed earlier operation with on_failure: continue freezes the resume cursor; later successful operations run again after interruption. Arbitrary raw expressions need not be idempotent either. A non-consuming raw Counter=Counter+1 predicate can accumulate committed damage until its per-run ceiling, which resets at restart.
Evidence: commit-then-Save sequence, absence of a key-range self-limit, cursor advancing only through an unbroken success prefix. SQL trigger consequence is inferred, not tested on SQL Server. Comments/documentation that call literal key-range replay safe overlook side effects and concurrent application changes.
Smallest fix: persist completed operations individually; preserve and surface ambiguous completion. Couple execution receipts to SQL transactions for exactly-once effects, or require reconciliation before replay of side-effectful work. At minimum exclude already-satisfied rows and explicitly document triggers, temporal/audit writes and at-least-once boundaries.

## F06 — SEVERE — Queue-lock deletion reopens the live-peer recovery race on Unix
Location: internal/run/lock.go:84–96; internal/run/lock_unix.go:17; internal/run/recovery.go:74, :206; internal/run/engine.go:1655.
Who: overlapping scheduled/default runs on Unix, requiring a narrow release/start race.
Schedule: A unlocks .sqlgopace.lock; B opens/acquires that same inode; A removes its pathname; C creates and locks a new .sqlgopace.lock. B and C both hold supposedly exclusive locks. C can now sweep B's processing directory while B is legitimately idle between statements. Recovery treats !Active as dead and requeues B's manifest. Duplicate DDL/DML follows; with abort_blocking_resumable: true a peer's paused build can be ABORTed, irreversibly discarding its progress. This is inferred from Unix flock/unlink semantics; not run on this Windows host.
Bound: the lock works for ordinary contention on the same existing file, but pathname removal breaks the invariant. Separate queues never exclude each other on the same database either.
Smallest fix: never unlink the lock file; keep a stable inode and only unlock/close. Add a deterministic interleaving test. For cross-queue conflicts, add server-side ownership/leases before adopting or aborting resumable work.

## F12 — MODERATE — Abrupt crash does not record ownership of the resumable it leaves behind
Location: internal/run/engine.go:967–984, :1124–1129, :1740–1768; internal/run/recovery.go:206–223.
Who: default resumable rebuild after process crash, rather than a gracefully classified interruption.

## Concurrency, interruption and failover synthesis

A single ordinary queue run is sequential, but “one DDL server-wide” is not enforced across working directories/machines. Independent queues can rebuild the same object, kill one another under broad blocker rules, or ABORT another queue's paused work. A running peer is not dead merely because dm_exec_requests has no row between its statements. F06 reintroduces exactly that same-queue exposure on Unix. A paused-operation ownership record contains operation ordinal and object names, not a server-side ownership token: a stale local record can refer to a replacement operation on the same index.

A dead execution connection does not establish rollback/commit. repairIfBroken pings, tries to stop the old session, repins and restamps, but stopOrphan permits progress on probe error/unknown login identity. The safe behavior is to preserve uncertainty, not automatically assume no request survived. State's session identity is stamped at manifest start; a later repin updates Conn and its context marker, but the saved state does not get its SPID/login refreshed merely by noteRepin, making crash correlation stale.

For an AG failover, startup eligibility and resolved capabilities are snapshots. Pool monitoring/control connections and the pinned execution session have independent lifetimes; a listener can reconnect a pool call to a different server while the saved SPID belongs to the old one. No server identity travels with KILL. New-primary edition/settings/replica role are not re-detected by repairIfBroken. Most ordinary DDL will fail on a read-only secondary, but that is not a safe identity check for instance-wide KILL. Reconnect classification can exceed its nominal two minutes if an individual DMV call never returns. No failover was run here.

## 2. Vulnerabilities carried by the code

These are narrower than the production-harm inventory. Severity/rank remain those of the corresponding finding; the order here reflects exploitation under the stated ordinary-operator threat model.

1. **Loss of monitoring does not stop privileged work (F01/F07/F04).** An operational fault is sufficient; no attacker is necessary. Some operation paths deliberately ignore samples, and tempdb reads the wrong database's log. These violate the program's advertised control boundary.
2. **Control commands are not bound to the displayed/original session identity (F02).** Default fallback, automatic killers and manual confirmed selection ultimately use a bare integer SPID. Reuse or failover can terminate an unrelated transaction. No malicious SQL input is required.
3. **Unsafe recovery state and exclusion (F05/F06/F08/F12/F19).** Queue lock unlink race, content-insensitive fingerprints, detached watermarks and non-atomic SQL/local completion allow duplicate execution, skipped work, loss of progress and uncertain ownership. Tampering with local state can exploit these, but normal crash/edit/disk failure is enough.
4. **Certificate trust disabled in the release template (F13).** A network-positioned attacker can impersonate the database server because encrypt=true is combined with trustServerCertificate=true. This is a real security vulnerability on the default SQL-auth path, not merely a raw-manifest trust decision.
5. **Destructive output integrity and local confidentiality (F14/F18).** Replacement writes/renames can clobber approved work/evidence; writable output directories/symlinks can redirect writes. Local reports may expose DML values and capture application SQL. Filesystem access is required; a writable queue already grants the DB login's manifest privileges. No claim of privilege escalation beyond the OS/SQL account's rights.
6. **Overbroad kill selectors and stale identity (inventory/guard table).** Regex matching and client-supplied host/app labels are selection hints, not authenticated authorization. Four-character command-prefix validation is not a maintenance-only allowlist. Opt-in policy can kill ordinary application transactions.

**Arbitrary SQL in trusted manifests is an acknowledged capability, not by itself a newly discovered trust-boundary vulnerability.** Nevertheless, type/compression fields resembling safe enums execute unvalidated fragments (F18), and raw SQL can bypass confirmations, predicate caps, session hardening and monitoring assumptions entirely. An operator who grants sysadmin for tempdb shrink and reuses that login for third-party manifests grants corresponding arbitrary SQL power. The smallest improvement is to remove the surprising raw surfaces, not to promise that a typed operation name makes arbitrary text safe.

No evidence was found of a remotely reachable unauthenticated service or generated OS-shell execution. No SQL Server physical corruption was demonstrated. The data-integrity risks established here are deletion/alteration, repeated side effects, skipped changes and lost maintenance progress; they should not be mislabeled storage-engine corruption.
